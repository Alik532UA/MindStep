## Що це

Веб-гра-стратегія «Твій Хід»: утримати спільну фішку на дошці. Режими **Survive**,
**Arena** і **Maze**; грати можна проти ШІ, локально вдвох і онлайн.
Чотири мови (`uk`, `en`, `nl`, `crh`).

## Архітектура

- **Фреймворк:** SvelteKit **2** + Svelte **5** (виключно руни). Не «SvelteKit 5» —
  це різні речі, і плутанина в назві веде до пошуку неіснуючих API.
- **Профіль:** `static`, GitHub Pages, base `/MindStep`. `svelte.config.js`
  читає `BASE_PATH`, а в dev-режимі підставляє порожній рядок.
- **Стан:** headless-контролери — класи в `src/lib/controllers/`. Складна логіка
  UI (лобі, онлайн, налаштування) живе там, а не в компонентах.
- **Ігровий рушій:** візуалізація (`game-board`) **ніколи** не впливає на логіку
  (`GameEngine`). `center-info` лише відображає стан, не змінює його.
- **Атомарність:** оновлення стану гри атомарне. Очищення вибору гравця —
  на початку ходу, а не в кінці попереднього.
- **Модалки:** через `BaseModal` (glassmorphism), наповнення — сніпетами.
- **Сховище:** префікс `mindstep_`, єдине джерело — `src/lib/config/storage.ts`
  (`STORAGE_PREFIX`). Origin спільний із шістьма сусідніми проєктами.
- **i18n:** типізований, власна `translationSchema.ts` + `typedI18n.ts`.
  Словники — `.ts`, не JSON.
- **Логування:** `src/lib/services/logService.ts`. `console.log` заборонений.

## 🔥 Онлайн-партія: журнал ходів, а не поле стану

Онлайн побудований на **журналі ходів** у Firestore, і це рішення, а не деталь.
Стан партії — чиста функція від (`seed`, склад, журнал), тож у базі лежить лише
опис партії й самі ходи, а **стан не зберігається ніде**:

```
rooms/{id}                     опис кімнати: склад, статус, налаштування
rooms/{id}.match               опис партії: { seed, boardSize, players, settings }
rooms/{id}/moves/{seq}         ОДИН ХІД — створити можна лише раз
rooms/{id}/votes/{playerId}    голос, заявка, кінець партії
rooms/{id}/presence/{playerId} присутність
```

Що з цього випливає — і що НЕ можна ламати:

- **Клік не змінює дошку.** `handlePlayerMove` дописує хід; дошка ворухнеться,
  коли хід приїде назад перепрогоном. Не повертай локальне застосування «щоб
  швидше»: саме на двох станах, які доводилося примиряти, тут і виросли захисні
  періоди, прапорці «перемогу вже оголошено» й коментарі `// FIX: race condition`.
- **Хід — окремий документ, і його можна лише СТВОРИТИ.** Повторний запис того
  самого номера відкидає база, а не клієнт. Не переписуй на «одне поле стану»:
  тоді правило доступу неможливо звузити (власника документа немає), останній
  запис перетирає чужий, а «що нового» доводиться виводити порівнянням довжин.
- **Кожен запис має власника.** `playerId` тут — це `auth.uid`, і саме тому
  правила однорядкові. Голос — власний документ гравця, а не поле спільного.
- **Продовження після «немає ходів» — новий ВІДРІЗОК журналу**, а не правка
  стану: господар переписує опис (та сама клітинка, той самий рахунок, наступна
  черга) і стирає ходи. Лічильники відвідувань обнуляти окремо не треба.
- **Прострочені кімнати клієнт НЕ видаляє.** Щоб прибирати чуже, потрібне право
  видаляти чуже — а це готовий примітив «видалити всі кімнати». Вони просто не
  показуються.
- **SDK бази не живе в `.svelte.ts`** і не ініціалізується в тілі модуля.

Ядро: [`src/lib/sync/`](src/lib/sync/) — `matchLog.ts` (конверт + підставний
транспорт), `matchReplay.ts` (перепрогін), `FirestoreMatchLog.ts`,
`MatchLogGameStateSync.ts`. Тести — `matchReplay.spec.ts`: двоє учасників в
одному процесі, без мережі й ключів.

Повний стандарт — `sveltekit-canon/selection_criteria/v8/platform/CLOUD-DATABASE-v8.md`.

## Локальні пастки

| Пастка | Що саме |
|---|---|
| Dev-сервер бере **5173** | типовий порт Vite, спільний з усіма сусідніми проєктами; запису в `.claude/launch.json` для MindStep немає. Якщо там уже висить чужий dev-сервер, дивитись будеш чужий сайт. Playwright цього уникає — у нього власний **5373** зі `--strictPort` |
| Не запускай `npm run dev` сам | заблокує термінал. Попроси користувача |
| Firebase піднімається **ліниво** | `authService` більше не ініціалізує Auth у конструкторі: синглтон рівня модуля робив це на імпорті, і юніт-тест ігрової логіки падав у CI з `auth/invalid-api-key` ще до першого тесту. Не повертай нетерплячу ініціалізацію — тести знову вимагатимуть бойових ключів |
| `headless` залежить від CI | `playwright.config.ts` має `headless: !!process.env.CI`. Локально — headed, на раннері — ні: там немає X-сервера |
| Мультіплеєрні тести не в CI | `tests/e2e/online/` (2 файли) потребують емулятора Firebase і запускаються **лише вручну** через `npm run test:online`. Це навмисно: кімнати, створені тестом проти бойового Firebase, побачив би справжній гравець |
| У CI йде лише один e2e-файл | `tests/e2e/invariants.spec.ts` і `tests/e2e/html-lang.spec.ts`. Десять наборів у `tests/e2e/virtual/` не запускаються ніде автоматично — не вважай їх покриттям |
| Падіння юніт-тестів мусить бути видно | `test:report` друкує і в консоль, і в JSON (`--outputFile.json`), а `test-reports/` вивантажується артефактом при падінні. Не прибирай `--reporter=default` — без нього лог CI німий |

## НЕ РОБИ

| Заборонено | Замість цього |
|---|---|
| Svelte 4 API: `writable`, `readable`, `on:click`, `<slot>`, `export let` | `$state` / `$derived`, `onclick`, `{@render …}`, `$props()` |
| `console.log`, `console.warn` | `logService` |
| Ключі сховища без префікса `mindstep_` | `getStorageKey()` із `$lib/config/storage` |
| `localStorage.clear()` | вибіркове видалення за префіксом — origin спільний |
| Скрипти в корені проєкту | усе своє — у `scripts/` |
| E2E-файли з розширенням `.test.ts` | єдиний стандарт — `.spec.ts` |
| Бізнес-логіка всередині `.svelte` | контролер у `src/lib/controllers/` |

## Діагностика

`logService` має об'єкт `logConfig` із прапорцями за темами (`score`, `ai` тощо).
Для дебагу редагуй прапорці всередині `logService.ts`, щоб бачити лише потрібне.
**Після виправлення бага поверни `logConfig` у початковий стан.**

Окремий помічник — `npm run diagnose`.

## Команди перевірки

```
npm run check        # svelte-check, має бути 0 помилок
npm run lint         # eslint, 0 errors (попередження — записаний борг)
npm run lint:all     # eslint + knip (мертвий код і залежності)
npm run test:report  # юніт-тести Vitest, вивід у консоль і в JSON
npm run build        # збірка
npm run check:build  # інваріанти над build/ — ПІСЛЯ build
npm run test:online  # мультіплеєр під емулятором Firebase, ЛОКАЛЬНО
npm run check:rules  # правила доступу Firebase під емулятором — і в CI теж
```

`check:rules` — **єдина перевірка, що бачить правила доступу**. Решта гейтів
проходить однаково і на правильних правилах, і на «дозволити все»: правила не
потрапляють ні в `src/`, ні в `build/`, ні в `svelte-check`. Саме тому дірка
`allow read, write: if true` на всіх кімнатах прожила тут до аудиту. Форму коду
навколо бази тримає окремо `src/cloud-database.spec.ts` — він у звичайному
`npm test`.

Якщо емулятор скаржиться `port taken` — на 8080/9000/9099 лишився java-процес
від попереднього прогону.

`check:build` — єдиний гейт, що бачить дефекти, невидимі в `src/`: порожня
сторінка, canonical, `sveltekit-prerender` в адресах і CSP, яка у збірці
приходить `<meta>`-тегом, а не заголовком, як у dev. Будь-яке твердження про
ці речі робиться після нього, а не після читання коду.

Для e2e економний вивід: `npx playwright test --reporter=line`.

**Результат треба побачити, а не припустити.** Твердження «правило виконано»
робиться після прогону, а не замість нього (AI-AGENT-PITFALLS-v8 § 5.1).
Окремо: крок CI зі статусом `-` (skipped) означає «невідомо», а не «гаразд» —
усе нижче першого падіння пропускається (§ 1.4).
