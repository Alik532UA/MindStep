# Firebase: структура даних і принципи

Джерело правди про форму документів — [`src/lib/types/firebaseSchema.ts`](../types/firebaseSchema.ts).
Тут — принципи й причини; там — типи.

> Попередня редакція цього файлу обривалася посеред JSON-блоку на 36-му рядку і
> описувала одну колекцію з шести. Файл читався як опис бази й описував іншу
> базу.

## 1. Головне: правила доступу — єдина межа безпеки

Публічний конфіг Firebase за побудовою лежить у бандлі, тож адресу бази знає
кожен, хто відкрив сайт. Усе, що робить із базою клієнт, може зробити будь-хто
тим самим SDK із консолі браузера. Отже:

- **Правила лежать у репозиторії**: `firestore.rules`, `database.rules.json`,
  прив'язані через `firebase.json`.
- **Правила перевіряються гейтом, а не очима**: `npm run check:rules` піднімає
  емулятор і проганяє 31 випадок — 10 «застосунок мусить це вміти» й 21
  «сторонній не мусить цього могти». Правила «дозволити все» валять другий
  набір, «заборонити все» — перший, тож зелений результат неможливий випадково.

## 2. Кожен запис має власника

Це і є причина, з якої правила вдалося звузити. `playerId` у цьому проєкті — це
`auth.uid` (`roomService.joinRoom`), тому кожен запис прив'язується до автора:

| Шлях | Хто пише |
|---|---|
| `rooms/{id}` | господар і учасники кімнати |
| `rooms/{id}/moves/{seq}` | **лише створити**, і лише той, чий `by == auth.uid` |
| `rooms/{id}/votes/{playerId}` | лише сам гравець |
| `rooms/{id}/presence/{playerId}` | лише сам гравець |
| `rooms/{id}/messages/{id}` | автор; правити не можна нікому |
| `users/{uid}`, `rewards/{uid}` | лише власник |
| `leaderboards/{uid}_{mode}_{size}` | власник — видно з імені документа |

Доти вся партія лежала в одному документі `rooms/{id}` у полі `gameState`, який
писали обидва гравці. Власника не існувало, отже єдиний дозвіл, що не ламав гру,
був `allow read, write: if true` — **без авторизації**. Дірка була не в правилі,
а в моделі даних.

## 3. Стан партії не зберігається — він обчислюється

`rooms/{id}.match` описує партію: `{ seed, boardSize, players, settings }`.
`rooms/{id}/moves/{seq}` — журнал ходів. Стан дошки не лежить ніде: кожен
учасник отримує його перепрогоном ([`sync/matchReplay.ts`](../sync/matchReplay.ts)).

Що це дає:

- **Хід — окремий документ, який можна лише створити.** Повторний запис того
  самого номера відкидає база, а не клієнт, тож двоє, що одночасно займають
  номер, розв'язуються самі.
- **Немає взаємного перетирання** і немає межі «~1 запис/с на документ»:
  документи різні.
- **Пізній учасник доганяє перепрогоном**, а не отримує знімок — окремого
  механізму «синхронізувати того, хто спізнився» не існує.
- **Одне число (`seed`) заміняє всю початкову розкладку.**
- Вимога «обидва бачать те саме» стала **перевірною**: двоє учасників живуть в
  одному процесі на підставному транспорті (`MemoryMatchLog`), і питання стає
  звичайним `expect` — див. [`sync/matchReplay.spec.ts`](../sync/matchReplay.spec.ts).

## 4. Дві бази, і кожна за призначенням

| Дані | База | Чому |
|---|---|---|
| Присутність «онлайн зараз» | Realtime Database | `onDisconnect` виконує сервер, коли клієнт зник. У Firestore такого механізму немає |
| Усе інше | Firestore | запити, індекси, `limit`, сортування |

## 5. Запити мають межу

Кожен запит колекції несе `limit()`. Лобі читає щонайбільше 50 кімнат, і те саме
число стоїть у правилі (`request.query.limit <= 50`) — тобто запит без
обмеження база просто не виконає. Доти запит публічних кімнат не мав `limit()`
взагалі: читалися всі, і кожна несла повний стан партії.

## 6. Offline-first

Рекорди й нагороди спершу лягають у `localStorage`, а потім синхронізуються з
хмарою. Firestore — джерело правди для профілів, рекордів і налаштувань кімнат;
локальне сховище — для того, що має працювати без мережі.
