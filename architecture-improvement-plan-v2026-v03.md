# 📑 Аудит Коду та План Покращення (v03)

Цей документ базується на комплексному аудиті стану проекту станом на лютий 2026 року. Головна мета — забезпечити максимальну прозорість архітектури для AI-агентів та розробників.

## 📊 Частина 1: Результати Аудиту

### 1. Управління Станом (State & Reactivity) — **88/100**
*Фундамент: SSoT + Derived over Sync*
- [x] **SSoT:** Стан дошки, гравців та налаштувань централізований у `.svelte.ts` сторах.
- [x] **Derived Discipline:** Використовується `DerivedState` для складних обчислень.
- [ ] **URL as State:** Параметри гри (розмір дошки, режим) поки що не дублюються в URL (потрібно для F5).
- [x] **Runes Usage:** Повна відмова від Svelte 4 сторів на користь `$state` та `$derived`.

### 2. Архітектура та Потік Даних (Architecture) — **82/100**
*Фундамент: UDF + Separation of Concerns*
- [x] **Headless Engine:** `GameEngine.ts` повністю відокремлений від UI.
- [x] **Type Safety:** Використовуються інтерфейси для всіх станів та результатів ходів.
- [ ] **Unidirectional Flow:** Іноді спостерігається "протікання" логіки оновлення стану через `bind:` або прямі мутації в компонентах-віджетах.

### 3. Чистота та Побічні Ефекти (Side Effects) — **75/100**
*Фундамент: Purity + Effect Discipline*
- [ ] **Effect Isolation:** Деякі `$effect` використовуються для синхронізації станів, які можна було б обчислити через `$derived`.
- [x] **No State in Effects:** Циклічних оновлень не виявлено.
- [ ] **Cleanup Function:** Не всі ефекти (особливо таймери в сервісах) мають чітку логіку очищення.

### 4. Компоненти та UI (Component Design) — **92/100**
*Фундамент: Composition + DRY + KISS*
- [x] **Dumb Board:** `GameBoard.svelte` не має залежностей від сторів.
- [x] **Snippets:** Використовуються для кастомних шарів дошки та модалок.
- [x] **Locality of Behavior:** Логіка обробки кліків знаходиться поруч з елементами.

### 5. Продуктивність та Стабільність (Performance & Stability) — **85/100**
*Фундамент: Performance + Error Handling*
- [x] **Keyed Blocks:** Використовується `{#key bState.boardSize}` для повного скидання дошки.
- [x] **Error Boundaries:** Весь лейаут гри загорнутий в `ErrorBoundary`.
- [ ] **Lazy Loading:** Можна покращити завантаження важких компонентів (ReplayViewer).

### 6. Безпека та Доступність (Security & A11y) — **70/100**
*Фундамент: Safety*
- [x] **HTML Injection:** `{@html}` не використовується.
- [ ] **Interactive Elements:** Багато `div` з `onclick` без повної підтримки клавіатури (`onkeydown`).

## 🛠️ Частина 2: План покращення та пріоритети

### 🔴 Високий пріоритет (Importance: 90-100)
- [ ] **Створити `BaseGameController` (95):** Винести спільну логіку з `local` та `virtual-player` в один контролер для запобігання дублювання та помилок при рефакторингу.
- [ ] **Ізоляція `animationState` (90):** Переконатися, що `GameEngine` жодним чином не залежить від стану анімації. Анімація має бути "підписником" на події двигуна.
- [ ] **Валідація через Zod (90):** Додати схеми валідації для `CombinedGameState` перед виконанням ходу.

### 🟢 Низький пріоритет (Importance: 30-50)

## ⚠️ Надважливі застереження (Guardrails)

1.  **Візуалізація vs Логіка:** `GameBoard.svelte` та шари (`*Layer.svelte`) мають залишатися "тупими". Дані про анімацію (`visualPosition`) мають існувати лише в `DerivedState` для UI, але не в `GameEngine`.
2.  **Незалежність режимів:** Будь-які зміни в `src/lib/gameModes/` мають тестуватися як для локальної гри, так і для віртуального гравця.
3.  **Збереження логіки:** Не змінювати алгоритми в `GameEngine.ts` без оновлення відповідних тестів (`settingsLogic.test.ts`).
4.  **Атомарність:** Оновлення `boardState`, `playerState` та `scoreState` після ходу має відбуватися синхронно (в одному тику).
